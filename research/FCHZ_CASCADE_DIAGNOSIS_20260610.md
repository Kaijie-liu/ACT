# FCHZ adaptive cascade diagnosis (2026-06-10)

This note audits the 2026-06-10 adaptive-cascade run described in the
continued session log.  The goal is to separate a promising result from an
audit-ready claim.

## Executive summary

- The run completed: `2836/2836` jobs, no duplicate `(benchmark, iid)` keys.
- Raw result: `1514 CERT + 681 FAL = 2195 V/A` on the 14-benchmark scope.
- The result exceeds the working targets `2000+` and `2065+` on this scope.
- It is not yet a paper-grade headline because the current artifact lacks
  complete CERT/FAL receipts and was originally produced by `/tmp` scripts.
- The run used one FCHZ adaptive cascade policy, not `hybridz_tf` fallback.
- The run was CPU-oriented (`HYZOR_FCHZ_USE_CUDA=0`, ORT CPU replay), despite
  earlier discussion using the phrase "GPU".  Treat it as a CPU/HiGHS cascade
  result unless rerun with a documented GPU path.

## What is solid

1. Coverage of the declared 14-benchmark scope is internally consistent:
   all iid ranges are complete and there are no duplicate result rows.
2. The cascade is a single FCHZ backend policy:
   Stage 0 FCHZ closed-form, then FCHZ MILP refinements with fixed stage order.
   No `hybridz_tf` fallback was found in the worker path.
3. Solver use is within the revised principle:
   `scipy.optimize.milp` / HiGHS only; no Gurobi import or commercial solver call
   was found in the FCHZ cascade path.
4. FALs are not generated by random sampling or PGD.  They come from LP/MILP
   solution extraction plus ORT replay.
5. Unit tests currently pass:
   `act/back_end/fchz_tf/tests`: 61/61
   `research/fchz/tests`: 9/9

## Issues that must be fixed before final claim

### 1. Artifact reproducibility

The run was produced by `/tmp/cascade_worker.py` and
`/tmp/cascade_full_run.py`.  A copy was placed under
`audit_results/fchz_adaptive_cascade_20260610/`, but `audit_results/` is
ignored by git via `.git/info/exclude`.

Action:
- Promote the worker/runner into versioned scripts, or store a small immutable
  manifest under `research/`.
- Record exact commit, dirty diff, conda env, scipy version, and command line.

### 2. CERT receipts are too thin

`CERT` rows currently record the mechanism and stage, but not the full solver
receipt.  For MILP CERTs, the artifact must include at least:

- solver status code and message;
- objective value for each certified row;
- threshold and strict slack;
- time limit;
- MIP gap / node count if exposed by SciPy/HiGHS;
- number of continuous and integer variables;
- constraint counts.

Without that, `309` MILP CERTs (`172` stage 1 + `137` stage 2) are promising but
not fully audit-grade.

### 3. FAL receipts are too thin

`FAL` rows include `lp_obj`, `t`, and truncated `ort_cy`, but not a full
replay receipt.  Each FAL should include:

- input-box check result;
- input hash or compressed witness artifact;
- ORT provider and output hash;
- violated row index;
- violation margin;
- no-clip flag;
- original ONNX/VNNLIB SHA.

The code path does perform ORT replay, but the artifact must prove it.

### 4. Scope is 2836, not the full 3453 table

This run covers 14 benchmarks.  The older comparison table used `N=3453`.
The current number can be reported as:

> FCHZ adaptive cascade: 2195 V/A on the declared 14-benchmark, 2836-instance
> scope.

Do not write it as a full-suite 3453-instance headline until the missing
benchmarks are either run or explicitly counted as zero.

### 5. CPU/GPU wording

The worker sets `HYZOR_FCHZ_USE_CUDA=0` and ORT uses `CPUExecutionProvider`.
The result is not a GPU verification result in the strict sense.  This is not a
soundness problem, but it is a reporting problem.

### 6. Principle boundary: spec-aware ReLU selection

`forward_global_milp.py` computes an approximate `d_eff` by walking backward
through dense weights to choose which ReLUs receive binary indicators.  This is
not CROWN-style bound propagation and does not enter the proof, but it is a
backward-looking selection heuristic.  If the advisor interprets "no backward"
strictly as "no backward computation of any kind", replace this with a
forward-only width/slack score.  If allowed, disclose it precisely as
selection-only, not bound propagation.

## Fixes applied in this audit pass

1. `adaptive_cascade.py`: added `input_shape` parameter for strict ORT replay,
   so image-shaped FAL candidates can be replayed with the original ONNX input
   shape instead of flat fallback.
2. `/tmp/cascade_worker.py`: updated to pass the ONNX input shape into the
   cascade.  This affects future reruns, not the existing 2195 file.
3. `forward_global_fal.py`: removed `np.clip` from the legacy FAL helper.
   Box-violating candidates are now rejected rather than clipped.
4. `README.md` and `__init__.py`: updated P3 wording to the current rule:
   open-source LP/MILP is allowed; Gurobi/commercial solvers are not.

## Recommended next audit sequence

1. Make the cascade runner a versioned command, not a `/tmp` script.
2. Add full solver receipts to `solve_forward_milp_lb`.
3. Add full FAL replay receipts to `adaptive_cascade`.
4. Rerun a stratified audit:
   - all `681` FALs for strict replay receipt generation;
   - all `309` MILP CERTs for solver-status receipt generation;
   - a small sample of `FCHZ closed-form` CERTs against independent bound code.
5. Rerun failed rows:
   `56` subprocess timeouts, `11` worker errors, and `2` accelerator errors.
6. Decide and document whether the backward-looking `d_eff` selection heuristic
   is allowed.  If not, replace it before the final run.
7. Only after 1-6 should `2195` be frozen as an audit-grade number.

## Bottom line

The result is real enough to be strategically important: the FCHZ cascade
finally crossed `2000+` on a large declared scope and reached `2195 V/A`.
However, it is not yet safe to present as the final paper or competition number.
The next work is not more algorithm exploration; it is receipt hardening,
scope clarification, and reproducible rerun infrastructure.
