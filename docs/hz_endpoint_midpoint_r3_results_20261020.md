## 失败位置与迟到证据

外层会话记录 `SESSION_CLEANUP_ValueError`，只保存异常类型而没有具体 message、PID、
读取阶段或首次异常。后续审计因此拒绝“已静止会话”，没有将子进程输出升级为成功。
记录的 RSS 峰值低于 2 GiB，且不足 10 秒就返回；它不是预算耗尽的证据。

| 同一 monotonic 时钟事件 | 时间（秒） |
| --- | ---: |
| component actor 完成记录 | 11264538.074817862 |
| 外层 execute 结束 | 11264538.881111870 |
| 宿主接收到负终态 | 11264538.884294787 |
| controller 观察到 actor 退出 | 11264538.959054152 |
| controller COMPLETE 记录 | 11264538.996735640 |

controller 在宿主返回后约 **0.112441 秒**才记录 COMPLETE。因此其文件虽已保存并绑定
正确，也不能补成在线完成。`remaining_session=[]` 可能是初始化值：若扫描抛异常，新的
扫描结果尚未赋给 `final`，空表不能证明当时已无后代。稍后的只读进程快照未发现 SID
810019 或宿主 PID 809420；这只是后续观测，不改写原清理失败。

[owned_session.observe](../scoped_proof/owned_session.py)存在可检验的竞态：先读 `stat`
保存非 zombie 状态，再读 `status`；进程在二者之间退出时，`VmRSS` 可能缺失，引发
`ValueError('live process RSS unavailable')`。清理再次调用同一观察器，异常又覆盖首次错误。
这个路径与结束时序相符，但现有记录不能排除其他 ValueError 门，**根因尚未唯一定位**。
本轮只做源码和记录诊断，不修改观察器，不新做故障控制。
