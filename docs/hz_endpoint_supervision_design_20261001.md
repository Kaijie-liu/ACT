# HybridZ endpoint CPU supervision protocol

This stage tests complete execution accounting for the existing tiny guarded
HybridZ endpoint algorithm. It does not change its mathematics or admit a real
model, full-size object or GPU. Freeze this protocol before implementation and
execution. The preceding endpoint controls remain intact.

## Scope and fixed calls

[The configuration](../configs/hz_endpoint_supervision_20261001.json) fixes four
normal calls and ten injected-fault calls. Each independently creates its live
HZ fixtures inside its budget. Separation, shared input and independent input
are the same sources, properties and gates as the preceding archive. The partial
case uses separation and deliberately omits the last pair's candidates. The full
pair roster remains present, so its checked result must be UNKNOWN.

The source-basis hashes include expert count, class count, properties, context,
every pair's original entry and expert snapshots, gate and relation mode. They
exclude the freshly built joint batch, whose independent-input frame is allocated
at runtime. The independent checker must reconstruct that batch's factor mapping,
constraints and exact endpoint objectives; a new hash is not permission to alter
the frozen source. New candidates are generated for every executed call.

## Execution and acceptance

Reuse the explicit-policy lifecycle engine and bounded owned CPU executor without
global patching. CPU admission and release explicitly say no CUDA was initialized;
release is process cleanup, not a GPU-driver observation. Each call uses one CPU
thread, a 2 GiB sampled RSS limit, and at most 300 seconds. Normal/error calls use
30 seconds; deadline injections use the shorter frozen budgets. Publication and
phase cleanup reserves are inside that same clock.

Charge imports, fixture creation, shared/private merge, exact query construction,
all 128-step proposals, prefix and final serialization, independent exact checks,
reception, cleanup and final API publication. Preserve operation events; nested
timings are explanatory and are not added twice. The parent anchors phase output
bytes and fixed launch plans before the next process starts. The checker cannot
be chosen or rebound by the producer. An externally observed, timely API return
is required for budget acceptance; valid files alone are insufficient.

Save the complete request once and append a full-roster proof prefix after every
completed pair. Missing candidates are null, not dropped obligations. A timeout
may leave mathematically checkable prefixes, but it cannot receive an online
positive conclusion. The independent checker rechecks all available bounds and
the full coverage aggregation. A completed nonpositive or partial check is a
completed execution, not a complete positive proof.

## Controls and stop rule

The fixed faults cover fixture creation delay, proposal exception, delay after
the first pair, serialization delay, wrong source, missing endpoint, checker
exception/delay/missing output and receiver delay. Every expected fault must
retain a bound injection event proving that the intended point was reached;
an earlier timeout does not pass that control. Additional record-only mutations
test source/parent-checker binding, inventory deletion, cost omission, late API
return and missing observations. Do not rerun only failed slots or tune a budget
to change a mathematical result; retain complete attempts.

This closes neither network-to-HZ lowering nor gate-range soundness. A positive
result remains conditional on the supplied guarded HZ and gate premises, not
native floating-point SAFE or a real MoE certificate. All six goal gates remain
open. CPU controls do not retry the refused physical GPU batch. After this stage,
review the actual costs and capacity boundary before any separately scoped next
experiment; do not automatically enlarge the fixtures.
