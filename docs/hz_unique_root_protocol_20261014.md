# Direct evidence identity and unique root resource protocol

Design assessment, 2026-10-14, based on `f5baf0e599d6674fa079047b884e594ba36b5475`.
The user authorized a new protocol without replaying old JSON logical bytes or
counting aliased roots as separate stored facts. This does **not** authorize
resource increases, production implementation, real models or GPU execution.

In the proposed format, two representation-specific obstacles are removed while retaining the
mathematical checks. Its complete **single-store format envelope** is about
96.8 MB for native binary64 candidates. Its specified exact-core arithmetic and
owned-data envelopes are finite. **The complete runtime/capture cost upper is
not yet closed:** native workspace, runtime allocation, live checkpoint capture
and implementation correspondence remain necessary. No quota is selected and
no full-topology execution is admitted. A bounded data format is not a proof of
300-second completion or of an 8-GiB RSS bound.

The [static calculation](../scripts/assess_unique_root_protocol.py) and
[machine-readable ledger](hz_unique_root_protocol_20261014.json) bind fourteen
existing source/report files. They read metadata and code, not checkpoints,
inputs or saved numerical arrays. The previous
[wire assessment](hz_wire_capacity_20261014.md) remains unchanged and continues
to describe that implemented version.

## Scope and unchanged obligations

The registered shape is router `3072–128–8`, eight experts `3072–256–128–10`,
eval selected-softmax top-2, CPU float64 candidate generation and exact rational
acceptance. The scope is a complete **captured declaration** of this shape;
binding it to a live trained checkpoint and bounding that loading/capture phase
are separate unfinished requirements, not free preprocessing.

All registered tie-legal pairs remain obligations, including pairs not proved
reachable. This conservative coverage list is not a route-change witness.
Input containment, source affine centers and compensation, ReLU inclusion,
factor identity/private ownership, guard direction, gate ranges, property
identity, dual sign and complete residual checks are retained. Both roles remain
required. Positive acceptance stays strictly above `1/10000000`; incoming
stored rationals retain 4,096-bit limits and accepted working results retain
8,192-bit limits. Nonpositive or partial evidence is not UNSAFE.

The shared/private factor representation and V3 enclosure mathematics do not
change in this proposal. No claimed algorithm, GPU or external-comparison gain
follows from the new encoding. G1–G6 remain open.

## New identity without old JSON expansion

Use a new domain-separated package identity, provisionally
`ACT_MOE_DIRECT_UNIQUE_ROOT_DRAFT_V1`, over canonical typed section descriptors,
their lengths/hashes, the source identity, request, mathematical-policy identity
and separately versioned resource-policy identity. Do not require reconstruction
of the old JSON byte stream or pretend the new hash equals an old forest hash.
Historical evidence keeps its original checker/schema; no old positive bound
is imported merely because the new graph describes the same intended network.

Source tensor bytes are stored once, preserving their original binary64 bits.
First-affine rows name a checked tensor, row, column range and the already
checked contiguous input factor map. They do not hide an arbitrary variable
length map in the fixed-size descriptor;
other locals/references remain explicit typed records. All source positions,
including zeros, are checked. Binary64 decoding is exact, not rounding an
arbitrary rational into a shorter representation. Hash checking supplements
rather than replaces semantic checking.

A coefficient node denotes a factored linear form. A root is the pair
`(center or rhs, node_id)`, not merely its coefficient vector. Under the
registered constructor, each newly allocated node has one root value;
stable/Flatten/common/pair aliases reuse it. The new checker must independently
establish this invariant and the complete source-derived sequence. Thus the
stored root-value bank has `Q <= N = 19,496` entries.

The **uses** of those roots are separate typed membership indices. Each use
retains view, output/equality/inequality kind, order, parent and factor scope.
All up-to-136,232 memberships remain checked and charged. Identical coefficients
with different centers, owners or guard roles must not be merged. An alias may
refer to a previously checked whole sequence only after its expected identity
and order are checked; a shortened or reordered sequence is not an alias.
The complete 336 pair-guard inequalities remain represented. Conceptually
expanding the checked membership indices recovers each V3 view's ordered
root values, without serializing that expansion. Since the source node forms,
scales, scopes and candidate coordinates are unchanged, the checked same-candidate
residual and weighted support are unchanged. This argument requires *all* the
source/alias checks; storage identity alone does not establish equivalence.

The new resource vector therefore separates unique values, memberships,
source positions, local tails, reference edges, active factors, candidate
entries and byte/lifetime costs. It does **not** divide the old root count by
some compression factor and treat the old limits as implicitly increased.
Every current production cap remains unchanged; any new cap mapping or numeric
ceiling requires later approval.

## Complete proposed store inventory

One attempt has one owned store. Each payload is written once; partial and
final indices refer to the same bytes. A temporary member becomes final by
rename, without a second full copy. An interrupted prefix remains charged,
unaccepted evidence with its actual length/hash recorded. No retry is hidden
in the same attempt. Published raw candidates precede acceptance receipts.

The native profile contains exact binary64 proposed duals plus an explicit
zero-vector role descriptor. The checker still validates both role identities,
row counts and signs and computes both bounds; zero is not omitted evidence.
Every endpoint has fixed binary binding fields, not an unbounded JSON record.
Computed bounds use up to 2,064 bytes per rational: two 1,024-byte magnitudes
and sixteen tag/sign/length bytes. Incoming generic rationals instead require
up to 1,040 bytes at the unchanged 4,096-bit bound.

| Component upper in bytes | Width 1 | Width 8 |
|---|---:|---:|
| Captured source and manifest | 59,909,824 | 59,909,824 |
| Forest, unique roots and membership indices | 16,861,088 | 16,861,088 |
| All native candidates and their index | 11,535,616 | 11,428,096 |
| Endpoint receipts, property results, gates and index | 4,428,096 | 4,428,096 |
| Code, metadata, events, logs, failure and terminal | 4,034,560 | 4,034,560 |
| **One complete store** | **96,769,184** | **96,661,664** |
| Two retained copies | 193,538,368 | 193,323,328 |

These are conditional **format envelopes**, not observed file sizes or limits
that this document has activated. Every field/member must satisfy the specified
encoding envelope; otherwise the future checker refuses rather than truncates
mathematical evidence. Arbitrary dense rational candidates are not covered by
the native envelope: with the same fixed binding fields and both advisory
`lower=0` fields, their complete-store uppers are
1,501,114,784 and 1,501,007,264 bytes. No lossy conversion is permitted to make
them fit. An upper above a limit does not prove a particular file exceeds it.

The forest envelope is

`256F + 64N + 16(L−W1) + 16R + 16N + 4H + 8F + 512V + 1 MiB`.

The factor record includes its generated name (at most 200 ASCII bytes), kind,
owner/scope and typed fields. The node record includes its source descriptor;
there is no extra descriptor bank. The captured-source header remains bounded
by 4 MiB. There are 95 source chunks for the registered canonical tensor layout.

For T candidate tiles, candidate bytes are
`8EM + 512E + 256T + 256 KiB`, with T=504 or 84. Width 8 uses pair-local groups
8, 8, 2; no nonexistent extra endpoints are charged as real queries.
Diagnostics occupy
`E(512+3×2064) + D(128+2064) + P(128+4×2064) + 256 KiB`.

Auxiliary bytes are fully itemized: at most 32 checker files ×64 KiB; a 16-KiB
code index; four 64-KiB execution-metadata files; a 256-KiB store index;
(504+32) events ×512 bytes; 1 MiB combined stdout/stderr; 64 KiB failure context;
and an 8,192-byte terminal. A stream overrun stops the attempt and records that
failure; it cannot drop required events and still claim completed accounting.
This is a proposed bounded checker distribution, not a finding that the current
transitive code inventory already satisfies it.

The maximum file inventory is 648/228 members, including source, proof, results,
code and failure records. The terminal contains only status, counts, bounded
costs and hash/length references to the separate result and inventory members.
It does not embed 252 property rows. Candidate/result growth is preflighted
before append; no unlisted scratch file or second proof body is allowed.

Moving a package to another location for a test does not delete the original.
Two retained copies have the upper above and cannot be promised within the old
128-MiB aggregate envelope. Relocation, checkpoint duplication, environment
installation and additional attempts are outside this single-attempt store;
their costs must be separately included, not hidden or retrospectively erased.

## Exact work and file traffic

The direct reader must provide constant-address descriptor access backed by
an owned immutable byte bank. It must not call the old lazy JSON-compatible
`NodeTable` from the inner affine loop. This avoids the old extra decoder work,
but source coefficient visits and repeated mathematical uses remain charged.
The byte bank must have no writable alias exposed to the native process; a
read-only mmap of a still-mutable external file is insufficient.

The static ledger retains V3 algebraic phase bounds, replacing only repeated
root-value parsing with Q unique root records. New membership uses are counted
separately. This yields the following **specified-core** bounds:

| Core visits or evaluations | Width 1 | Width 8 |
|---|---:|---:|
| Production record visits | 26,519,040 | 15,792,660 |
| Production coefficient visits | 2,161,406,048 | 1,298,519,408 |
| Production exact-expression evaluations | 4,273,366,725 | 4,273,366,725 |
| Additional role/index accesses per pass | 17,094,140 | 14,688,380 |
| Portable replay exact-expression evaluations | 4,245,621,013 | 4,245,621,013 |

The full phase formulas are in the JSON ledger. This is not a measured count,
a bit-operation bound, a new Work quota or a seconds prediction. Construction,
source validation, gate planning, objective pullback, candidate API, dual
acceptance and aggregation all remain. In particular, batching duals does not
remove the current per-endpoint objective pullback. The plan is nowhere near an
established 8M complete-work contract; representation changes do not erase the
billions of conservative exact-core evaluations.

If a separate portable recheck is required before online acceptance, it must
run before the same deadline and its complete count is added. The ledger
includes that sum rather than treating it as a free audit. A later offline
check has its own reported cost and cannot repair a timed-out online request.

The candidate schedule remains 129 adjoints and 128 forwards per tile, CPU
float64/one thread, the same projected updates, rate and proposed/zero policy.
These native operations are not zero cost simply because they do not call
`Work.exact`. A bounded layout replacement must preserve the mathematical
algorithm; changed floating reduction order may change candidates and must be
disclosed and controlled. The existing strong CPU implementation stays a
reference. No new matrix-free or GPU kernel is authorized by this proposal.

For a store envelope B, a proposed four-pass file schedule gives reads <=4B
and writes <=B: input intake, independent online source
checking, portable replay and parent reception each scan bounded immutable
members at most once. Per-row source accesses thereafter are RAM traffic,
which still costs time. The current code does not meet this schedule merely
because these formulas exist. One file pass is **not** one hashing pass:
chunk/tensor, section/member, semantic/query and inventory identities all remain
required. The new design bounds **named hash contexts**, not just file passes:

- At most 2B payload bytes per pass: member digests and a disjoint second
  partition (whole tensors for source chunks; typed sections for the forest).
- Additional overlapping semantic frames per pass are bounded by
  `4 MiB + 8192 + (264F+64) + (576V+4H) + P(8M+256+16384)`
  `+ 4096D + 2176E + 16384`. These cover request/contract, factor identity,
  view scopes, row rosters/gates, properties, queries/slots and small root bindings.
- Each of at most `2×members + 53 + V + 4P + D + 2E + 16` contexts also has
  at most 64 domain-prefix bytes. The package root commits to the bounded
  inventory member; it does not expand that inventory into the small root frame.

Five conservative passes cover four reads and publication. A future named-context
dispatcher must charge every `hasher.update` byte and refuse unlisted or excess
uses. Within an immutable checked session it may reuse these identities, never
skip mathematical comparisons or coverage checks. This conditional bound repairs
the invalid inference that four reads and one write imply only `5B` hashing.
It gives **1,050,950,880 / 1,049,606,880 hash-input bytes** for widths 1 / 8.
Gate frames contain only the four checked scalars and bounded bindings;
query frames contain the registered ten-class coefficients and rational offset.
They do not include dense residuals or expanded visible-factor sets. Any such
additional hashed object needs its own bound instead of using the small frame
allowance; factor-scope checks still operate on the complete declared graph.
Optional copying adds B read, B written and `2B+128×members` member-hash bytes;
an independent semantic recheck is additionally charged. Original checkpoint reads, canonical
scalar decoding, exact-runtime internals and memory traffic still need a fixed
implementation account; they are explicitly not included in a claimed full
request Work upper.

## Memory and complete cost closure

The proposed constructor must stream typed source/forest records directly.
It cannot retain a full old JSON declaration, decoded Fraction bank, global
Python COO lists, all candidate JSON or a joined second proof. The parent
holds only a bounded index/log window. Constructor/native execution and the
portable child are sequential; child termination and resource release precede
the next child. Two simultaneous full consumers are not within this envelope.

A conservative persistent exact-data layout reserves

`S(w) = 2w(N+F) + 4(N+F+M+n) + 16E`

rational slots. It covers alpha/objective/residual vectors, source/norm/scale
state, current-row bookkeeping and endpoint scalar records without assuming
sparse duals or small numerators. At 2,064 bytes per slot this is 702,618,624
bytes for width 1 and 2,192,034,048 bytes for width 8. Including the immutable
source/forest bank, one raw candidate tile and two 64-KiB stream buffers gives
owned typed-data bounds of **779,542,976 / 2,269,113,184 bytes**.

This requires a future bounded representation and a proof that all persistent
objects fit those slots. It is not the current Python dict/Fraction memory
size. Existing 8,192-bit checks occur *after* expression evaluation: even a
simple sum of two such rationals may need a 16,385-bit unreduced numerator.
That observation is not a complete gcd, interpreter or allocator scratch bound,
and it does not raise the accepted bit limits.

The full required formula is

`RSS_parent + max(RSS_construction, RSS_native_and_exact, RSS_portable)`,

with each phase including owned payload, mapped pages, runtime/interpreter,
arithmetic scratch, native kernel scratch and allocator-retained memory.
Those remaining terms are not yet bounded for a pinned implementation. The
current 8-GiB RSS and 16-GiB address-space stops remain **stop rules**, not
proof that all obligations will fit or complete. Checkpoint loading/capture
has an additional missing envelope. No wall-time forecast is inferred.

| Closure item | Current status | Required before implementation or execution freeze |
|---|---|---|
| New canonical identities and scoped unique roots | Specified | Small lossless/semantic differential and mutation controls |
| Complete single-store member envelope | Conditionally closed | Code inventory, bounded writers and lifecycle correspondence |
| V3 exact-core counts and indexed uses | Conditionally closed | New primitive/memory traffic ledger and checked implementation correspondence |
| Named hash contexts and file traffic | Conditionally closed | Dispatcher, immutable-session and no-hidden-pass controls |
| Exact persistent payload | Conditionally closed | Bounded layout, arithmetic scratch and allocator proof |
| Native workspace | Open | Pin actual dispatch/allocation or separately approve and control a bounded layout |
| Live checkpoint capture and full RSS | Open | Bound input loader, runtime and parent/child lifetimes |
| Numeric resource ceilings | Not selected | Complete common upper for both arms, then explicit approval |
| Full-scale or real/GPU execution | Not authorized | Separate freeze and approval after admission |

## Controls required after a separate implementation decision

The next control stage, if later approved, must include root aliases with
different centers/owners, illegal guard reuse, missing/reordered memberships,
private-factor overlap, corrupt source ranges, canonical rational extremes,
signed zero/nonfinite source bytes, both candidate roles, missing endpoints,
partial writes, identity swaps, byte/bit overflows and before/after-deadline
receipt handling. Recompute all duties in a relocated `python -I -S` package
without model/data/history/solver access; charge copying separately.

Exact same-candidate results must match the prior mathematical path on bounded
controls, even though hashes/encodings differ. Controls must demonstrate that
the new code never materializes old JSON or repeated root-value banks, that
native code cannot mutate the checked source, and that all costs—including
refusal, cleanup and terminal publication—fit inside the common 300-second
request clock. Passing such controls would establish an interface prerequisite,
not a trained-model certificate or external advantage.

The current stage performs static arithmetic and identity tests only. It does
not claim those implementation controls have passed. Stop before quota changes
or real execution while the full-runtime cells above remain open; do not replace
them with another small timing run, a cap value or an extrapolated prefix.

navigation, review-handoff and manuscript-preservation regressions pass
