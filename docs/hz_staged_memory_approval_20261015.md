# 分阶段内存监督的具体审批方案

2026-10-15；起点 `648378f8482709fba5a329d659d98999952cf09e`。
承接已冻结的[监督设计](hz_staged_memory_protocol_20261015.md)，本方案提出
**每进程 256 MiB AS、20 次全链控制、一个组件控制批次和一次真实 OS 限额探针**。
这是待批方案，不是执行配置；[机器记录](hz_staged_memory_approval_20261015.json)
中 `approval_granted=false`、`active_as_bytes=null`。没有修改旧协议或运行新 worker。

## 一个额度及其依据

拟定 `AS_BYTES=268435456`，watchdog、controller、actor 使用相同 soft/hard 值。
每次最多一个 actor，故设限后的条件化虚拟空间包络为 805,306,368 字节，即
768 MiB。它不是完整 RSS、启动前内存、内核资源或成功容量证明。保留原来的
2 GiB RSS 采样拒绝、128 MiB arena／归档、8M Work、全部数学门及 300 秒。
不设置 512 MiB 回退，也不做额度搜索。

这是一项面向小型标准库控制的资源政策选择，不是从观测推出的必要或充分额度：

| 已有记录 | 数值 | 允许的解释 |
| --- | ---: | --- |
| 分页 r3 的 15 次 COMPLETE，旧 caller＋worker group 采样 RSS | 56,709,120–59,183,104 B | 旧路径的观测，未记录 VmSize，不能证明新 AS 足够 |
| 最大已记录 owned arena／保留文件 | 943,252／474,174 B | 微型 fixture 的部分成本，不是 Python 堆上界 |
| 最大已记录 Work | 21,686 | 旧控制成本，不是新监督或真实模型成本预测 |

数据来自[冻结分页记录](hz_paged_result_controls_20261015.json)，只重新读取归档，
没有重跑。另一次普通 `act-py312 -I -S -B` 只读环境检查看到 4,096 字节页、
AS soft/hard 为 unlimited；最小解释器 VmSize 为 21,188 KiB。这仅是启动环境
观察，未导入新监督器、未设限、未分配探针，不作为完整路径容量保证。

若 256 MiB 下启动或任一固定控制无法完成，就记录失败并停止，不据结果提额。
注册八专家对象的两遍来源合法性下界 13,922,736 Work 仍超过 8M；此方案不试图
解除它，也不准入真实模型、原生优化器或 GPU。

## 明确接口与终态布局

冻结设计 JSON 中的 `dense_reference` 是描述标签；现有实际 method registry 使用
`kind="dense"`。本方案显式绑定 `dense_reference → dense`、
`pair_scoped → pair_scoped`，不修改旧文件或同一 schema 的语义。两臂的候选宽度
仍为 8，检查宽度分别为 8／2。

提出仅用于控制元数据的 `STAGED_MEMORY_CONTROL_V1`：平坦 JSON、85 个固定字段、
全部值为固定宽度 ASCII 字符串，sort_keys、无空白分隔、无尾换行。不是来源矩阵
编码，不取代原始有理数、候选、结果页或独立复算。字段与宽度完整列于机器记录。

- 身份为 64 个小写十六进制字符；尚未建立时使用 64 个 `-`，最终角色必须拒绝
  必需身份缺失。枚举使用固定允许集合、右侧空格补足长度，不能放任意异常文本。
- 整数为 20 位十进制字符串，值域 `[0,2^64-1]`，左侧补零；未知量为 20 个 `-`，
  不得解为零。标志为 `0/1/?`，profile 只允许 `0/1`，均由阶段语义再次核对。
- 禁止转义、非 ASCII、重复键、未知字段、嵌套容器或错宽值。读取前检查长度，
  解析前检查平坦词法结构；不能先无限解析再检查字段。
- `proof_complete` 仅指本次来源合同下全部必要数学义务已检查；接收器仍须从完整
  引用结果强制核对 `native_float_proof=false` 与
  `checkpoint_correspondence_checked=false`，不能升级为原生执行或 checkpoint 保证。

按这些规则，每份记录物理长度固定为 **4,202 字节**，与保守字符串长度公式和
标准库 JSON 编码的计算一致，低于原 64 KiB 门。这是设计布局核算，运行时 codec
尚未实现或通过故障控制。

六个 suffix 路径保持原协议不变，其中前三个控制记录各 4,202 字节，后三个日志
各至多 256 行、每行 256 字节（含换行）。日志只有固定事件码、时间和有界数值；
生成前检查额度，不调用任意异常 `str/repr`。stdout/stderr 必须经有界捕获，
不能让异常输出直接绕过日志预留。成功 suffix 上界为 **209,214 字节**；仍从原
总额度预留 393,216 字节和六成员，不挪成额外数据容量。

关闭顺序为 receive 日志→receive tail→controller 日志→controller tail→
watchdog 日志→terminal。已关闭项不得再追加；异常路径只能作非接受结束。
各记录自身及尚未存在的后继 hash 使用缺失哨兵，后继记录／有界 IPC 绑定其实际
hash。terminal 自己的长度恒为 4,202，可先计算总字节，再一次编码；自身 hash
只放外层 IPC，不在文件内递归计算。watchdog 的最终代码不得在封存日志后继续写
日志或 payload。最终 caller 只保留有界返回记录，不新增第七个在线文件；批次工具
之后保存它属于另列的离线归档，不补救在线超时。

## 固定控制表

### 八个完整基准

B01–B08 严格使用 `half/guarded × dense/pair_scoped × profile 0/1`，每请求 300 秒。
每条必须实际执行生产、fresh portable 的两遍完整源／端点检查，随后由受监督
RECEIVE 聚合和外层接收。搬迁、旧路径访问拒绝和导入前外部代码校验内置于所有
八条，不再为它们增加一批模型请求。

比较对象固定为旧 r3 同一八组合的逐义务结果；机器记录绑定具体旧请求、bundle、
index、source 与规范化 `{"summary":...,"rows":...}` 的哈希。准备阶段核对了
bundle→manifest→index→pages 的内容哈希和完整行顺序，没有执行旧求解器。
该档案差分不证明旧路径被重新数学核验；新路径仍必须独立计算全部新结果，不能
读旧答案作为候选或接受依据。它也不是新旧执行时间的性能比较。
旧档只由批次审计器在新请求结束后读取，不进入 PRODUCTION／PORTABLE／RECEIVE；
读档审计成本单列，不属于新请求的 300 秒在线证据预算，也不能救回超时或失败。
同候选差分还须绑定未修改的 `FIXED_SCALAR_STUB_V1` 实现及实际 profile：本方案
增加 `direct_lifecycle.py` 的代码锚，实施冻结时再次核对，不能只凭结果 hash
相同推出候选相同。

### 十二个全链异常或边界控制

除下表指明外，固定 `guarded / pair_scoped / profile 0`。不把故障乘以八组合。

| ID | 固定触发点 | 请求时限 | 必须观察到的结果 |
| --- | --- | ---: | --- |
| F01–02 | guarded 两臂分别修改下界，重算全部归档 hash | 300 s | 到达 fresh 数学逐行比较后拒绝，不是只拒旧 hash |
| F03 | 合法 missing candidate | 300 s | 全部遍历后 complete UNKNOWN，不是部分完成 |
| F04 | 首页发布后异常 | 300 s | ERROR，保留前缀与成本，不启动后续阶段 |
| F05–08 | 构造、生产端点、PORTABLE、RECEIVE 各一次阻塞 | 各 10 s | 已进入目标故障点后 TIMEOUT，无晚到接受 |
| F09 | half/scoped/0，最终发布阻塞 | 10 s | TIMEOUT，完整计费 |
| F10 | half/scoped/0，watchdog 正常结束，但 caller 收取已过期 | 10 s | TIMEOUT，不能凭 COMPLETE 文件接受 |
| F11 | half/scoped/0，写出看似成功终态后 watchdog 异常退出 | 300 s | INCOMPLETE_TERMINAL，不信任准备好的成功文件 |
| F12 | RECEIVE 注入 MemoryError | 300 s | 非接受、固定错误码；不是 OS 限额验证 |

短时限只用于失败控制，不改变成功请求的 300 秒。未到达指定故障点必须记录
`CONTROL_NOT_REACHED`，不能作为通过，也不能自动加时。F09 和 F11 只在已确认
controller 与 actor 全部退出后触发，不故意留下孤儿进程。F09 是实际不返回的
最终发布阻塞：caller 持有尚未回收的专用 watchdog PID，截止时只对这个 owned PID
定向终止、有界回收，不盲目 killpg，也不操作已回收或身份不明的 PID。计费包含
这段清理；回收失败记 `CLEANUP_INCOMPLETE`，不得只写 TIMEOUT 后留下进程。其他
watchdog 异常仍按原协议保留可能未完成的子组清理状态，不据此扩大终止权限。

### 一个有限组件批次

C01–C11 的 **33 个固定变异**列于机器记录：默认关闭／批准身份、角色与前驱、
source/method/property、导入前代码篡改与旧路径、义务缺失／重复／错序／多余、
计数或截止重置、prefix/suffix 非法项、编码／日志超限、EXDEV／目标冲突、
进程观察／reap 失败、危险异常格式化。

一个受限标准库 actor 在共同 300 秒内依序检查这些有限变异；不重建模型、不启动
真实额外子进程。进程异常由固定观察接口 stub 给出，不能把 stub 通过当 OS 进程
隔离证明。未完成变异保留为未完成，不给每项重开 300 秒。代码与方法保持默认关闭。

### 一次真实 OS 限额探针

M01 单列、同样需要批准。由受监督 actor 使用标准库 `mmap`，controller 从该
owned PID 的 `/proc/<pid>/limits` 独立读回；两方必须核对 soft=hard=256 MiB，
且 `0 < VmSize ≤ AS_BYTES`。actor 先进行有界握手，等待 controller 读回后才执行
探针，避免进程先退出导致记录缺失。在同一 300 秒内只做两次匿名私有、`prot=0` 映射：

1. 映射一页并关闭，必须成功。
2. 映射长度恰等于 AS_BYTES，必须得到真实 `OSError(ENOMEM)`；若意外成功，立即
   关闭并判控制失败。任何其他错误、缺失报告或超时都不算通过。

不触碰映射页面，不创建巨大 bytearray，不扫额度。依据是
[Linux AS 对 mmap 的限制及继承语义](https://man7.org/linux/man-pages/man2/getrlimit.2.html)与
[Python 标准库匿名映射接口](https://docs.python.org/3.12/library/mmap.html)。
记录准确描述为“限额读回一致，观察到越界映射拒绝”，不能声称单一 ENOMEM 排除了
其他资源原因，也不能把 F12 注入替代这一项。caller 的自身限制必须前后不变。

## 审批后的实施顺序与停止条件

拟请求一次明确批准：采用上述 256 MiB 值，实施默认关闭的新版本，并仅执行此处
20 次全链请求＋一个组件批次＋一次 OS 探针。不得把此方案自动标为已批准。

实施时先完成 codec／bootstrap／进程组／接收接线，静态检查实际编码不超过上述
布局、检查点保留和依赖清单完整，再提交／推送确切运行配置及实现哈希后执行。
运行前检查机器资源和已有任务；不干预其他用户。控制日志和未完成前缀使用新目录
保留，不拼接历史 r3。任何未预期拒绝、控制未命中或身份漂移均停止本批，后续项
登记 NOT_RUN；修复后重跑需新的执行身份，不自动改变额度或控制范围。

通过意味着生命周期与接收控制成立，不意味着新增 HybridZ 算法收益、真实证书、
GPU 加速或完整模型准入。下一次研究决策仍需面对独立的 Work／表示容量限制。
