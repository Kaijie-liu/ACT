# 原生候选出口与完整内存准入裁决

**同一 binary64 候选可以不经过整批有理数字符串而无损进入现有精确检查器；这只消除
中间表示，不解决完整候选流额度或原生运行内存。** 对现有安装的只读 ELF 核查还发现：
`libtorch_cpu.so` 单个可执行映射就需 274,377,021 字节，超过拟议的 256 MiB AS。
因此该标准库小控制方案不能成为导入 Torch 前生效的完整原生容量合同。

## 无损出口的数学与身份合同

当前 `Operator.propose()` 对整个 tile 执行 `.tolist()`、`Fraction`、字符串化，然后
`direct_candidates.encode()` 又解析全部字符串。对任意有限 binary64 值 v，
`Fraction(v)` 与 `rational(str(Fraction(v)))` 是同一个有理数。直接保存其 binary64
字节，再由 `_native()` 恢复 Fraction，不改变候选。分子／分母最多1075位，仍在
原4096位限制内。负零必须规范为正零：旧 Fraction 路径会消去符号，现有接收器拒绝
负零字节；NaN／无穷仍必须拒绝。

拟议出口只读取原优化选出的 best 对偶，不改变128次更新、选优或回退：

- frame 内按 equality、inequality 排列；native `groups` 却是 ine、eq，不能直接串接。
- 保留所有行、proposed／zero两角色、精确零 advisory lower、完整槽位／query／source／
  contract／ordinal绑定及缺失标记。零角色仍写完整向量，不在本次加入压缩格式。
- 保留原消费者对每条不等式对偶符号、显式零、原始来源系数、残差补偿与正阈值的检查。
  负下界和缺失义务不能成为 UNSAFE 或完整正结论。
- 同一候选、同一绑定任务可要求与现有 profile0 encoder **字节相同**；旧 JSON 与
  二进制的哈希本来不同，跨格式比较应核对数学下界和接受，而非整个 receipt 字节。

这是一条表示等价推导，不是新算法效果或实现正确性证明。现有 Lifecycle 仍只接受
固定 stub；新原生出口及其配置身份尚未接入。

## 去掉字符串仍不能保证完整候选流准入

现行 profile0 每 tile 的准确格式长度为

\[
F(k,M)=128+k(72+2\times1040+16M).
\]

M 是 equality 与 inequality 行数之和；两角色都占空间。注册范围为 k≤8、M≤2700，
28个pair各有最多18端点，满目录分块为8、8、2，而不是每个tile都有8端点。

| 项目 | 字节 |
| --- | ---: |
| 最大8端点frame | 362,944 |
| 2端点尾frame | 90,832 |
| 84个tile／504端点完整流上界 | 22,868,160 |
| 原独立候选流cap | 16,769,024 |
| 上界与cap之差 | 6,099,136 |

完整流上界超过cap表示统一容量保证缺失，不说明每个实际请求都会超限。去掉字符串
不会改变上述字节，不能借整归档89,165,848字节的条件上界取消独立流门；新实现若增加
代码／metadata，还必须重新计入归档，不自动继承这个整包数值。

## 有界出口必须先结束优化对象的存活

在旧 `propose()` 末尾直接使用 generator 不够：被挂起的函数仍可能保存 alpha、
residual、points、groups及其z／best。只有优化函数结束、仅移交受身份绑定的best对偶，
且不存在外部可写别名／旧frame引用，才可使用下面的**条件命名载荷**。

| 出口选择 | 最大frame相关存储加best对偶 |
| --- | ---: |
| 新增owner内部直接填写，fill与seal同时存活 | 2×362,944＋172,800＝898,688 B |
| 沿用现有 `Driver.receive()`，外部raw＋fill＋seal | 3×362,944＋172,800＝1,261,632 B |

其中best对偶为8×8×2700＝172,800字节。第二条的外部raw不在现有owner arena账本内，
不能漏计第三份。两条都尚未接到原生生命周期；不要据此新增一个单独控制批次。
标量与对象头、来源、roots、精确arena、常驻native bank、原生scratch、分配器和异常
traceback均不在该小计内。引用释放也不保证RSS归还。

完整路径的存活关系仍需逐阶段绑定：来源构造／检查期间保留Packet、Snapshot和图；
native准备又与检查来源重叠；候选期间Driver已经准备roots（dense还准备objectives）；
精确消费期间native bank若为下一tile常驻，就仍与精确工作区共存。两次fresh来源检查
仍独立执行；候选流出口不能变成“信任之前检查过”的捷径。

现有抽取＋encoder在满目录E=504、T=84、M≤2700下的计数上界可单独定位为：

| 原阶段 | Row visits | Coefficient visits |
| --- | ---: | ---: |
| native字符串抽取 | 1,008 | 1,360,800 |
| encode及allocate／put／seal | 672 | 5,444,796 |

合计上界6,807,276，之后Tile还有最多504行header检查；不是已执行计数。
它们是旧完整账本中的组成，不能再叠加。
新出口应替换这些对应操作、记录新增读取／封口／复制／发布／释放；其完整新Work上界
现在为空，不能把删除字符串转换等同于删除消费者或获得免费候选。Fraction/string、
native和I/O未调用 `Work.exact`，也仍属于300秒真实成本。

## 已安装库给出了独立的地址空间拒绝证据

本机 `act-py312` 安装版本文件为 Torch 2.9.1+cu128、源码身份
`5811a8d7da873dd699ff6687092c225caffcf1bb`。只读解析其 `libtorch_cpu.so`
64字节ELF头和616字节program-header表，得到：

| 静态映射量 | 字节 |
| --- | ---: |
| 最大可执行PT_LOAD的MemSiz | 274,377,021 |
| 五个不重叠LOAD的原始MemSiz之和 | 345,320,329 |
| 拟议标准库控制AS | 268,435,456 |
| 仅可执行LOAD已超出的量 | 5,941,565 |

记录绑定这段元数据的哈希与文件长度，不声称哈希了整个库或证明其算术实现。上述是
虚拟映射，不是RSS，也没有运行动态加载器。在标准ELF加载路径下，若256MiB限制
在原生导入前生效，这个库映射本身就不能容纳，尚不需要考虑模型、堆、其他库和
GEMM scratch。先导入再降低上限不会自动卸载已有映射，更不能借此声称全流程符合该容量。

安装的 `ATen/Config.h` 启用MKL、非sequential MKL及OpenMP，但这些宏不能独立绑定
将来具体调用的后端dispatch。`CPUBlas.h` 的double GEMM只有接口声明，没有调用方
workspace预算或内部容量上界。[旧原生核查](hz_runtime_lifetime_20261014.md)针对
COO到`axpy<double>`模板的direct-loop路径，不能转用为GEMM的证明。单线程限制也
不能推出scratch为零。**GEMM和完整进程的内存上界仍未闭合**，不是已证明不存在上界。

## 本轮收束与下一决策

本轮闭合的是无损候选出口的数学条件、两种具体接收路径的复制小计，以及256MiB不能
覆盖已安装原生库的额外静态理由。不是完整容量、算法增益、来源完整证书或GPU成绩。

**停止独立实施候选出口／小内存监督修补。** 它们不消除两遍来源至少13,922,736＞8M、
126,632成员＞65,536以及当前候选流的容量缺口。也不再继续搜一个更漂亮的局部字节数。

下一份实施决策必须联合限定：真实来源适配、可核验工作区的具体原生算子路径、候选
所有权、完整检查及两臂资源政策。对于当前未绑定工作区的GEMM，不能以经验峰值、
AS拒绝机制或任意安全倍数填上成功容量上界；也不自动扩展为自研BLAS项目。
这些选择未闭合前，完整捕获／heap／RSS及新额度继续为null，不启动实现或真实执行。
