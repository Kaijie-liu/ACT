## 固定范围和默认拒绝

[合同](../scoped_source/endpoint_batch.py)限制顺序为：组件；guarded 原搜索；
guarded 中点；mixed 中点；mixed 原搜索；中点非协作阻塞；截断候选发布。
组件仍为 22 项、三份合成来源、三次成功单 tile 搜索和一次预期异常搜索。
不得重试、恢复、跳过失败或按结果重排。失败后保留全部未执行后缀。

未来冻结必须同时绑定两臂的方法、同一来源、代码闭包、既有环境、全部额度、故障和
组件目录。新[批次批准表](hz_endpoint_execution_approvals.json)为空；两个既有原生
批准表未改。旧批准不能启动新代码；批次验权和原生 profile 验权都要通过。
本轮没有生成来源或登记任何新 profile。V2 仍拒绝新中点方法。

正常控制验收要求全部必要义务完成检查，不要求全部正界，也不要求两臂结果相同。
不同候选产生不同合法下界应保留，不以效果筛选控制。算法增量仍是最后一次更新使用
同 pair、同性质两个端点的 best 对偶中点；没有改 HZ、原数学检查或数值接受门。

## 单位置完整计时

[原生监督](../scoped_source/native_supervised.py)新增可选 `outer_started`。
不用该参数时原有时间安排不变；新批次从位置准备之前取得同一个起点：

| 边界 | 相对位置起点 | 包含的工作 |
| --- | ---: | --- |
| 受管执行截止 | 298 秒 | 准备、启动、加载、候选、检查、搬迁和接收 |
| 进程组清理截止 | 298.5 秒 | 仅清理本次拥有的进程组 |
| 原生调用者接收截止 | 299 秒 | 原生终态写入与回读 |
| 位置最终截止 | 300 秒 | 外层审计、完整文件清点、位置回执写盘与回读 |

两臂同用该安排，从原有 300 秒内预留收尾，不是增加预算。原生接受返回值与磁盘上的
预接收 `terminal.json` 分开绑定。`slot.json` 写入后才由批次记录实际观察时间；迟到或
缺失回执拒绝，不靠离线重查补成在线成功。

[组件监督](../scoped_source/endpoint_component_supervised.py)复用既有 owned 进程组
及有界 pipe 日志接收。受管 controller 先设 AS/FSIZE，再验证代码；组件 actor 设置
相同限制后加载原生环境。搬迁检查器不另建 session，继承同一绝对截止和累计 Work。
局部等待不再使用隐含无限清理等待的 `subprocess.run`；异常时由已有外层 owner
清理整个受管组。没有子检查器完整回执时，父计数只是观测前缀，剩余 Work 未知。

## 故障和终态审计

[终态审计](../scripts/audit_endpoint_midpoint_controls.py)不求解、不重证网络。
它核对冻结身份、位置顺序、来源和方法、实际返回值、各阶段累计 Work、全部义务汇总、
硬截止和进程组清理。

- 中点阻塞必须有唯一 JSON 到达标记，绑定来源、pair、方法及第 127 号评价后的
  `128/128/127/0` 计数，并确实被外层截止。前置错误不能代替阻塞控制。
- 截断发布标记绑定完整和截断 frame 的长度、hash、invocation、来源与第零 tile。
  审计核对实际少一个字节及预期 `OSError`，禁止后续阶段、完整结果或包被接受。
- 完成的正常请求核对 tile 数、评价、forward、更新及端点数量的累计关系。
  失败前缀保留；缺失 Work 不设为零或 complete。
- 位置审计失败但进程组已经清理、原截止尚有余额时，可记录文件成本；这不挽救判定。
  无法完整清点的成本显式未知。批次审计拒绝被替换的 `freeze.json`、额外目录、
  非法链接及未登记运行；失败位置不从分母消失。

## 制品和内存合同

原生位置增加一份至多 64 KiB 的 `slot.json`。组件元数据逐名绑定在合同内：

| 位置 | 元数据保守上限 | 文件数 | 来自的既有预留 |
| --- | ---: | ---: | --- |
| 原生正常或故障位置 | 7,798,784 字节 | 14 | 8 MiB、16 文件 |
| 组件位置 | 6,619,136 字节 | 10 | 8 MiB、16 文件 |

两者都在原 128 MiB、4096 文件内部，不提额。组件的三来源工厂目录（包括模板）、
原包及独立搬迁副本均保留计费；archive 在写入前扣除已有来源和元数据成员预留。
`external.json` 和 progress 在局部 archive/清点与全局预留中有保守重复，不据此
申请更多额度。整批七位置文件上限的合计为 896 MiB，另有最多 4 MiB、四文件的批次
元数据；这不是单请求新额度，也不代替实际清点。

对象寿命仍按以下共同驻留项记录，不将所有 Python 存储都称为原生 scratch：

| 阶段 | 同时保留的项目自有对象 |
| --- | --- |
| 组件来源构造后 | 三份 Packet 页和 index，三个 forest 的 node/factor/root/view/scale，来源 PackedRow bank |
| 候选及精确消费 | 算子；两组 best/迭代；alpha/value/residual/points；局部旧 `z` 引用；同一个精确 arena、Task 和 receipt |
| oracle/归档 | mixed 展开行字典；原 frame、换序/污染副本；tests/searches；archive entries/attempted/prefixes/events；文件和 hash 清单 |
| JSON/复制 | 尚存对象加序列化字符串、bytes 和单文件读取/复制缓冲；不是只有 64 KiB I/O chunk |
| 搬迁子进程 | 上述父组件和 Torch，加子进程独立来源/forest/检查器，以及外层 profile/清单/回执 |

这些对象分别受原有页、成员、行、因子、位数、tile 和 Work 门约束；本阶段没有声称
得到总 Python heap 或物理 RSS 的精确上界。每受管进程 8 GiB AS 是硬限制；2 GiB
是执行期间整个受管组加 owner 的采样停止门，不是完整请求峰值内存证明。收尾受
调用者 AS 和时间限制，但不在同一个 RSS 采样循环中。原生分配器、scratch 和系统
调用仍采用超限拒绝合同；不承诺这份合成完整批次必定能完成。

## 整批最后一个未闭合边界

驱动在脚本入口开始累计 2100 秒，包含参数、绑定、准入记录和批次收尾；剩余不足
完整 300 秒位置加 2 秒收尾时不启动下一位置。仅一次最多 60 秒的资源观察，无重试。
但脚本内计时不包含 Python 解释器启动，最终 `batch-received.json` 的时间也采样于
它自己的写入之前。若其最后 fsync 迟到，文件可能存在而调用失败。

因此，**不能让这些文件单独触发整批 PASS**。下一步只补一个可信启动者的有界
启动/返回观测，并绑定最后文件的及时接收、退出状态和完整成本；不得用再追加一份
自身写入前的“成功时间”解决这个问题。现有审计已经将这个缺口设为显式 pending 门，
不是文档脚注。启动者绑定进入同一冻结和累计时间，不能另给一个完整执行预算。

本批尚无执行批准。外层观测完成、静态核对后，才另行形成不可变冻结，取得新鲜准入和
执行授权。没有理由扩充控制项目、再改算法或开始真实模型/GPU。
