## 新核实的断点

### 1. 原生算法与共享表示可对接，但监督入口尚未对接

`check_scaled_references.checked()` 已接受完整、密封、同一累计 Work 下的
`CheckedSharedForest`；现有 CPU `Operator` 使用的 nodes/factors/scales/rows，以及
候选使用的 roots Sequence/Mapping，均有对应接口。两角色候选的字段和有限 binary64
对偶也与直接帧 profile 0 相容。**不能把这里描述成数学接口不兼容，也不用重新发明已有算法。**

然而，当前 `direct_supervised.spec()` 只接受 `half/guarded` 固定小源，`direct_method`
只登记 `FIXED_SCALAR_STUB_V1`，`Lifecycle` 直接实例化 `FixedProposer`。
worker 强制 `-I -S` 并拒绝 torch/numpy/scipy 导入。现有 native `produce()` 又是另一条
保留 raw 候选、JSON 编码、Session 聚合的旧路径，不是新版 Driver／直接帧／分页结果路径。
所以“类型可接”不等于已贯通，不能直接借用任一旧路径的成本作为新完整路径成本。

保留的 CPU 算法参考应是现有原生候选算法，而不是固定候选器。未来若比较 dense8 与
pair-scoped2 消费器，应在同一绑定来源、同一候选算法和共同资源政策下，先核验同候选
精确接受一致性，再比较完整请求。这个比较隔离消费表示，不单独证明新算法优于原始
HybridZ 或外部工具；原有强原生和外部对照仍须保留。

### 2. 拟议 256 MiB 不能成为完整路径的继承容量合同

现有 `Operator.__init__` 将所有 local entries 展成 `rr/cc/vv` 三个 Python 列表，随后
构造 int64 COO indices 和 float64 values。`torch.tensor` 的公开接口语义是复制输入
（本机现有 Torch 文档亦如此）。在 `sparse_coo_tensor` 参数准备齐全时，列表和两个
tensor 同时存活。对 64-bit CPython，设条目数为 L，仅这些存储就至少需要：

\[
B_{\mathrm{setup}}\ge3(8L)+2(8L)+8L=48L.
\]

注册拓扑允许首层权重全非零，因此该**允许形状的条件实例**满足：

\[
L\ge3072+6,684,672=6,687,744,\qquad
B_{\mathrm{setup}}\ge321,011,712\text{ bytes}.
\]

这比拟议的 268,435,456 bytes 多 **52,576,256 bytes**，尚未计 Python 数值对象、
源 bank、图、库、coalesce、转置和分配器。此论证不依赖 coalesce 是否另行复制。

**限定：**这不是实际 checkpoint 的非零数测量，也不是任意算法的空间下界。
旧 Work 等门会更早拒绝；上式假设未来其他准入问题已解决，只否定“直接接现有
Operator 后就可继承 256 MiB 的全形容量保证”。本次没有分配这些数组或调用原生算子。

另一个独立矛盾是现有 dense8 完整 all-present buffer 调度下界 **322,734,720 bytes**，
也超过该 AS 提案 **54,299,264 bytes**。未实施的 ownership-only 改写下界
212,116,800 不能充当现有实现上界。pair-scoped 检查内存较小，也不消除候选器的
全局 COO 和 `N×k` 工作区。

### 3. 共享来源还改变了原生准备成本

`SourceLocal.__iter__` 逐位置检查首层权重，包括零；原生构造再对非零 local 计费。
相对旧显式 local 来源，接入共享源至少新增 **6,684,672 次 setup 来源访问**。
这是一次准备成本，不是每次优化迭代都重新读取源；随后迭代使用物化后的 tensor bank。
不能沿用旧 native 的 Work 值，也不能把 scoped 检查器的 arena 当作 native 全工作区。

## 继续／停止裁决

**停止：**不继续运行已有小源控制来累积完成数，不实现尚未获批的 256 MiB 方案，
不重试完整形状，不用下界倍数定额度，不把源视图／生命周期接线重命名为算法创新。

**继续的有限静态问题：**是否能保留共享源行块，避免当前 `SourceLocal→全局 COO`
物化，并在完整候选与精确检查的对象寿命下给出可实现的两臂合同？这是现在有代码依据的
表示问题。必须同时列明来源读取、原生临时量、候选流和独立重算；原生算法已有的
DAG／尺度分离／伴随计算不算新增机制。若仍采用原生全局 COO，就如实保留上述内存
需求，而不是只修检查器。此处只是研究问题，不是该新算子的实施授权。

完整合同之后，资源政策是否另版、采用哪种来源适配、允许何种实现和执行，都须独立
冻结并获得相应授权。当前 300 秒、全部数学检查、接受门、位数及原额度不变。
G1 的完整请求算法增量、G2 的实际 GPU 收益、G3 同源完整正证和 G4/G5 外部／跨家族
结果均没有新增；历史 23 增益的来源缺口不变。G1–G6 仍 OPEN。
